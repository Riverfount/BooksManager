Versão 0.1.0 · Outubro de 2026

Este documento reúne a visão, a arquitetura e a stack tecnológica do Books Manager. Os requisitos funcionais, as regras de negócio e os requisitos não funcionais ficam em `docs/requisitos.md`; o diagrama de classes, em `docs/diagramas.md`; e as histórias de usuário, em `docs/use-case.md`. ## Visão geral

O Books Manager é uma aplicação web para organizar o acervo e os empréstimos de uma biblioteca escolar ou comunitária de pequeno porte.

### Problema

Bibliotecas desse porte costumam controlar livros e empréstimos em cadernos, planilhas ou mensagens de WhatsApp. Com isso, é difícil saber quais livros estão disponíveis, quem está com cada exemplar e quais devoluções estão atrasadas. As multas são calculadas à mão e não há histórico confiável do que foi emprestado.

### Objetivo

Oferecer ao bibliotecário uma forma simples de cadastrar o acervo, registrar empréstimos e devoluções, acompanhar atrasos e calcular multas automaticamente, mantendo as regras de negócio isoladas em um domínio testável. O sistema é composto por uma API REST (Java e Spring Boot) e por uma interface web separada (React e Tailwind CSS), em repositório próprio.

### Escopo da versão 1.0

A versão 1.0 é um projeto individual, com entrega prevista para 24/02/2027. Ela inclui o cadastro do acervo e dos leitores, empréstimos, devoluções, renovações, penalidades por atraso (multa ou suspensão, conforme a configuração), pesquisa, relatório de atrasos e controle de acesso por perfil. A política de penalidade por atraso é configurável pela biblioteca desde a primeira versão. Reservas e relatórios adicionais entram se o prazo permitir.

Ficam fora da versão 1.0: venda de livros, livros digitais, integração com sistemas contábeis, aplicativo móvel nativo, catalogação avançada (MARC21), acesso do leitor ao sistema e suporte a várias bibliotecas na mesma instalação (multi-tenancy).

## Arquitetura

O sistema segue a arquitetura hexagonal (portas e adaptadores) em um monólito modular. O domínio e os casos de uso ficam no centro, sem depender de framework. Tudo o que é externo (banco, interface web, e-mail, API de ISBN) se conecta por portas, que são interfaces, e é implementado por adaptadores. A regra de dependência é única: tudo aponta para dentro.

### Estrutura de pacotes

```
com.riverfount.booksmanager
├── catalog     (livros, autores, categorias, exemplares)
│   ├── domain
│   ├── application   (portas de entrada e saída, serviços)
│   └── adapter       (in.web, out.persistence)
├── loan        (empréstimos, multas, reservas)
│   ├── domain
│   ├── application
│   └── adapter
├── user        (leitores e usuários do sistema)
│   ├── domain
│   ├── application
│   └── adapter
├── security    (autenticação e autorização)
└── shared      (exceções, configuração e utilitários)
```

### Diretrizes

- **Domínio em Java puro.** Sem anotações de Spring ou JPA. As regras de negócio (prazos, multas, limites) ficam nas entidades e em políticas do domínio.
- **Referência entre agregados por identificador.** O empréstimo guarda o ID do exemplar e do leitor, não os objetos, o que mantém os agregados pequenos e desacoplados.
- **Tempo injetado.** O domínio recebe a data atual por parâmetro ou por `Clock`, em vez de chamar `LocalDate.now()`, o que torna os testes determinísticos.
- **Um caso de uso por interface**, com command próprio, implementado em um serviço de aplicação que apenas orquestra: carrega agregados, chama o domínio e persiste.
- **Portas de saída na linguagem do domínio.** Os repositórios e gateways são definidos pela aplicação, e a implementação com JPA fica no adaptador.
- **Entidade JPA separada do domínio** no módulo de empréstimos, com mapeamento explícito. Nos cadastros simples do catálogo, é aceitável uma abordagem mais pragmática, para evitar cerimônia sem retorno.
- **Comunicação entre módulos** por portas públicas. O módulo de empréstimos consulta o catálogo por uma porta de saída, implementada por um adaptador interno. Eventos de domínio ficam para quando houver necessidade real.
- **Transações** na camada de aplicação, no wiring ou com `@Transactional`, conforme a decisão de cada módulo.

### Política de penalidade configurável

A penalidade por atraso é uma política do domínio, com variantes para multa, suspensão, ambas e nenhuma. A devolução recebe a política vigente, lida da configuração da biblioteca por uma porta de saída, e devolve a penalidade a aplicar. Assim, mudar de multa para suspensão é uma alteração de configuração, não de código, e cada variante é testada isoladamente. Valores iniciais: ver RN08.

### Interface e API

A interface é uma aplicação React separada do backend, em repositório próprio, e se comunica com ele apenas por HTTP e JSON. Os controllers REST são os adaptadores de entrada da API: traduzem as requisições em commands dos casos de uso e devolvem DTOs próprios, nunca as classes de domínio. A API é versionada (`/api/v1`), seu contrato fica registrado no OpenAPI e o CORS é restrito à origem do front-end, configurada pela variável `APP_CORS_ALLOWED_ORIGINS` (issue #76): sem ela, nenhuma origem é aceita; só a rota `/api/**` é coberta e o filtro roda antes da cadeia de segurança, para o pré-voo `OPTIONS` (sem credenciais) não receber 401. O backend não guarda sessão no servidor.

Todos os recursos do catálogo (livros, autores, categorias e exemplares) seguem o mesmo contrato de CRUD, descrito a seguir. Os erros saem sempre em ProblemDetail (RFC 9457): 400 para requisição inválida, 404 para id inexistente e 422 para violação de regra de negócio.

| Operação | Rota | Resposta |
| --- | --- | --- |
| Cadastrar | `POST /api/v1/{recurso}` | 201 com `Location` e o recurso criado |
| Consultar | `GET /api/v1/{recurso}/{id}` | 200 com o recurso, inclusive inativo (`active=false`) |
| Listar | `GET /api/v1/{recurso}` | 200 com uma página (`PageResponse`) |
| Editar | `PATCH /api/v1/{recurso}/{id}` | 200 com o recurso atualizado |
| Inativar | `DELETE /api/v1/{recurso}/{id}` | 204 sem corpo |

#### Compatibilidade do contrato

O contrato da API é o OpenAPI gerado pelo SpringDoc (`/v3/api-docs`), e o front-end, em repositório próprio, depende dele. As regras para evoluí-lo dentro de `/api/v1`:

- **Não quebram** e podem entrar a qualquer momento: campo novo na resposta, parâmetro opcional novo na requisição, endpoint novo e valor novo em um enum de resposta que o cliente trata como desconhecido. O cliente deve ignorar campos que não conhece.
- **Quebram** e exigem uma versão nova (`/api/v2`): remover ou renomear campo, mudar o tipo de um campo, tornar obrigatório um parâmetro que era opcional, mudar o significado de um código de status ou de um valor existente.
- Toda mudança de contrato é citada na descrição da PR que a introduz e anotada na tabela abaixo, para o repositório do front-end acompanhar.
- Campos obrigatórios (issue #85): nas respostas, cada campo que a API sempre devolve é marcado com `@Schema(requiredMode = REQUIRED)` e fica em `required` no OpenAPI; os que podem ser nulos (`publisher` e `publicationYear` do livro) ficam de fora. Nas requisições, o `required` vem do Bean Validation (`@NotNull`, `@NotBlank`, `@NotEmpty`), e as de edição (`PATCH`) não exigem nada. O `OpenApiRequiredFieldsTest` confere isso; ao criar um `*Response` novo, marque os campos da mesma forma.

#### Listagem e paginação (RNF14)

- Parâmetros `page` (a partir de 0), `size` (de 1 a 100, padrão 20) e `sort` no formato `campo[,asc|desc]`, com os campos permitidos definidos por cada listagem. O `active` vale `true` por padrão, então os inativos só aparecem quando pedidos.
- Filtros próprios de cada recurso: `name` em autores e categorias; `bookId` e `status` em exemplares; `title`, `author`, `isbn` e `categoryId` em livros (ver "Livros", abaixo).
- A resposta é um `PageResponse` com `items`, `page`, `size`, `totalItems` e `totalPages`.
- Tamanho acima de 100, página negativa, campo de ordenação desconhecido ou filtro com valor inválido (um `status` inexistente, por exemplo) são recusados com 400, e nunca ajustados em silêncio.
- No núcleo, a paginação usa os tipos `PageQuery` e `PageResult`, de `shared.domain`, em Java puro. O `Pageable` do Spring Data fica restrito aos adaptadores de persistência, que o obtêm por `SpringDataPages` (em `shared.adapter.out.persistence`) e desempatam a ordenação pelo `id` para as páginas serem estáveis.

#### Edição com `PATCH`

- Usa JSON comum, não JSON Merge Patch. Só os campos enviados são alterados, e um campo omitido ou `null` mantém o valor atual; por isso não é possível "apagar" um campo obrigatório por essa rota.
- Os campos enviados seguem as mesmas regras de formato do cadastro.
- Campos imutáveis não fazem parte do DTO e, se vierem no corpo, são ignorados: o ISBN do livro (RN01), o código de patrimônio e o livro do exemplar.
- Quando o campo editado é único (o nome da categoria, por exemplo), a checagem ignora o próprio registro, porque manter o valor atual não é duplicidade. A restrição `unique` do banco é a defesa final contra a corrida entre a checagem e a gravação; para o `UPDATE` também ser traduzido em regra de negócio, o adaptador grava com `saveAndFlush`.

**Livros.** O conjunto `authorIds` enviado substitui o atual e nunca pode ser vazio. Categoria e autores só precisam existir e estar ativos quando são novos para o livro; os que ele já tinha continuam aceitos mesmo inativados depois (HU18, HU21).

**Pesquisa de livros (RF05).** É a própria listagem `GET /api/v1/books`, com filtros opcionais que valem em conjunto: `title`, `author` (nome de um dos autores) e `isbn` casam por trecho, sem diferenciar maiúsculas, e `categoryId` casa pelo id. No ISBN, hífens e espaços do termo são ignorados; nos textos, `%` e `_` valem como caracteres comuns. Toda resposta de livro (cadastro, consulta, listagem e edição) traz `availableCopies`, a quantidade de exemplares **ativos** com status `AVAILABLE`. A contagem pertence aos exemplares, não ao agregado `Book`: os casos de uso devolvem `BookWithAvailability` (o livro e a contagem), e a página inteira usa uma única consulta agregada em `CopyRepository.countAvailableByBookIds`, sem uma consulta por livro; o `BookSearchQueryCountTest` garante isso, comparando o número de consultas de uma página pequena e de uma grande (quatro por página: a página, o total, os autores em lote e os exemplares disponíveis). O autor é filtrado com `EXISTS`, então um livro com vários autores que casam aparece e é contado uma vez só.

**Exemplares.** Só o status é editável, e a regra fica em `Copy.changeStatus`. A rota manual aceita as transições para `DAMAGED` e `LOST` e a volta para `AVAILABLE` de um exemplar `DAMAGED` ou `LOST` (recuperado ou consertado). `BORROWED` e `RESERVED` só mudam pelos fluxos de empréstimo, devolução e reserva, e um exemplar emprestado não pode ser marcado como danificado ou extraviado por essa rota (RN10); a transição não permitida devolve 422. `markAsDamaged()` e `markAsLost()` não têm essa trava, para os fluxos de empréstimo poderem usá-los.

#### Inativação com `DELETE` (RN14)

- Nunca exclui fisicamente: inativa o registro. A resposta é 204, e inativar um registro já inativo é idempotente (também 204).
- O registro inativo continua acessível em `GET /{id}` com `active=false`, sai das listagens padrão e mantém suas associações (os livros de um autor inativo continuam com ele), mas não pode ser usado em cadastros novos.
- Um livro inativo não aceita exemplares novos (o cadastro de exemplar devolve 422). Um exemplar `BORROWED` não pode ser inativado (RN10) e também devolve 422.

### Verificação automática

Testes com ArchUnit garantem no build que o domínio não importa Spring nem JPA, que a aplicação não depende dos adaptadores e que o domínio não depende da aplicação. **Implementado** (issue #4): `ArchitectureTest` (renomeada de `ArquiteturaTest` na issue #41), com as três regras via `archunit-junit5` (o `pom.xml` tinha o artefato `archunit` core, sem o módulo de integração com JUnit 5 — trocado por `archunit-junit5`). ## Banco de dados e migrações

- O esquema é criado e alterado somente por scripts do Flyway, no padrão `V<número>__<descrição>.sql` (dois underscores), na pasta `src/main/resources/db/migration`.
- O Hibernate roda com `ddl-auto=validate`, apenas conferindo o esquema, e com `open-in-view` desativado.
- Ordem sugerida das migrações: catálogo (livro, autor, categoria, exemplar), leitores e usuários, configuração da biblioteca, empréstimos e multas, reservas.
- Restrições no banco reforçam as regras de negócio: ISBN único, código de patrimônio único e controle de versão otimista na tabela de exemplares.
- **Estado atual**: `V1__create_catalog.sql` (issue #6; nomes de tabela e coluna traduzidos para inglês na issue #41, já que o banco ainda não tinha dados reais) cria as tabelas `category`, `author`, `book`, `book_author` e `copy`, com as restrições de RN01 (ISBN único) e RN02 (código de patrimônio único), e a coluna `version` em `copy` para o lock otimista de RNF17. O `@Version` da entidade JPA que a usa de fato veio na issue #16, com teste de concorrência determinístico (duas cópias do mesmo exemplar, a segunda a salvar falha com `ObjectOptimisticLockingFailureException`). Aplicada e verificada tanto por Testcontainers quanto contra o PostgreSQL real do `compose.yaml`.
- **Leitores**: `V2__create_reader.sql` (issue #88) cria a tabela `reader` com só os dados mínimos de RNF11 (nome, documento, e-mail, telefone, data de nascimento e dados do responsável), documento único e obrigatório, `active` verdadeiro e `blocked` falso por padrão, e índice por nome. A exigência do responsável para menores de 18 anos é regra do domínio, não do banco. Verificada por `ReaderMigrationTest` com Testcontainers.
- **Usuários do sistema**: `V3__create_app_user.sql` (issue #97) cria a tabela `app_user` (`id`, `login`, `password_hash`, `role`, `active`), com login único e obrigatório, `role` restrito a `ADMIN` e `OPERATOR` por `check` e a senha só como hash BCrypt, sem coluna de senha em texto puro (RNF07). O nome é `app_user` porque `user` e `system_user` são palavras reservadas do PostgreSQL (`system_user` foi o nome previsto na issue, mas faz o `create table` falhar); a classe de domínio continua `User`. Verificada por `AppUserMigrationTest` com Testcontainers.
- **Domínio do usuário** (issue #98): `User` e `Role` (`ADMIN`, `OPERATOR`) em `user.domain`, em Java puro. O hash da senha chega pronto e o domínio não conhece o BCrypt (o codificador é uma porta de saída), então só confere que o hash existe e cabe na coluna. O login é obrigatório, sem espaços, com até 50 caracteres e **guardado em minúsculas**, para não diferenciar maiúsculas (a restrição única do banco passa a valer sem distinção); buscas por login devem usar `User.normalizeLogin`. `changeRole`, `changePasswordHash` e `deactivate` (idempotente) alteram o estado, e `canAuthenticate` é falso para o usuário inativo (RF08). Regras que dependem de outros usuários (login único, não deixar o sistema sem administrador) ficam na aplicação.
- **Persistência do usuário** (issue #99): porta `UserRepository` (`save`, `findById`, `findByLogin`, `existsByLogin`, `count` e `findAll` paginado com `UserFilter`) e `UserFilter` (login por "contém" e `active`) na aplicação, com entidade JPA separada (`UserJpaEntity`, tabela `app_user`) e mapeamento explícito. O adaptador normaliza o login em `findByLogin` e `existsByLogin` (sem diferenciar maiúsculas nem espaços nas pontas), de modo que a busca não depende de o chamador lembrar. O login duplicado é recusado pela restrição única do banco e traduzido em `BusinessRuleException`, também na edição; `findByLogin` devolve o usuário inativo para quem chama decidir (`canAuthenticate`). `count` serve ao administrador inicial (#100). A listagem filtra por login ("contém", `%` e `_` literais) e `active`, e ordena por `id` ou `login` (a ordem de `login` é a do collation do banco).
- **Administrador inicial** (issue #100): `CreateInitialAdminUseCase`, implementado em `UserService`, cria o administrador só quando `UserRepository.count()` é zero; o `InitialAdminRunner` (`ApplicationRunner`, adaptador de entrada em `user.adapter.in.startup`) o chama na inicialização com `app.admin.login` e `app.admin.password` (variáveis `APP_ADMIN_LOGIN` e `APP_ADMIN_PASSWORD`, vazias por padrão). O hash sai da porta de saída `PasswordHasher`, implementada com BCrypt por `BCryptPasswordHasher`, que tem o seu próprio codificador privado. Não há um bean `PasswordEncoder` global de propósito: enquanto a autenticação não existe, um bean assim faz o Spring Boot tratar a senha gerada do usuário padrão como hash, e o login provisório (`user` com a senha do console) deixa de funcionar; o `ProvisionalLoginTest` guarda isso, e o bean pode voltar com a cadeia JWT (#101). O resultado é `CREATED`, `ALREADY_HAS_USERS` (nada é criado nem alterado, então reiniciar é inofensivo) ou `NOT_CONFIGURED` (sem usuário e sem as duas variáveis: a aplicação sobe e avisa em log). Nenhum segredo vai para o log: o comando e as propriedades escondem a senha na forma de texto, e só mensagens fixas são registradas. Um login inválido nas variáveis (com espaços, por exemplo) faz a inicialização falhar com mensagem clara, em vez de seguir sem administrador.
- **Política de senha** (decidido em 15/10/2026; RF08, RNF07): de 8 a 25 caracteres, com ao menos uma letra maiúscula, uma minúscula, um número e um caractere especial (qualquer um que não seja letra, número ou espaço; o espaço é aceito, mas não conta como especial). A regra é `PasswordPolicy` no domínio, aplicada à senha em texto antes de gerar o hash, e vale para o administrador inicial (#100), a criação de usuário (#106) e a redefinição de senha (#110). A mensagem de erro lista só as regras não cumpridas e nunca repete a senha. Como o BCrypt só usa os primeiros 72 bytes, a política também recusa uma senha com mais de 72 bytes (possível com caracteres de vários bytes, mesmo dentro dos 25 caracteres). No administrador inicial, uma senha fraca faz a inicialização falhar com essa mensagem; com qualquer usuário já cadastrado, a variável é ignorada e a senha não é conferida.
- **Cadeia de segurança e JWT** (issue #101; decidido em 15/10/2026; RF08, RNF04, RNF08, RNF09, RNF10):
  - A `SecurityFilterChain` (módulo `security`, pacote `security.configuration`) é stateless: nenhuma sessão é criada no servidor, o CSRF fica desligado (ele protege cookies de sessão) e o resource server do Spring Security valida o token JWT do cabeçalho `Authorization: Bearer`. O filtro de CORS continua antes da cadeia (o pré-voo não leva token).
  - **Rotas públicas:** `/api/v1/auth/**`, `/actuator/health`, e a documentação (`/swagger-ui.html`, `/swagger-ui/**`, `/v3/api-docs/**`). A documentação é pública por decisão do dono do projeto, inclusive em produção (o SpringDoc avisa em log que pode ser desligada, com `springdoc.api-docs.enabled` e `springdoc.swagger-ui.enabled`). Todo o resto exige autenticação.
  - **Token:** HS256 com um segredo único, `APP_JWT_SECRET` (variável de ambiente), de ao menos 32 bytes; a aplicação não sobe sem ele, com uma mensagem que não repete o valor. O `JwtDecoder` confere assinatura, emissor (`app.jwt.issuer`, `booksmanager`) e validade **sem tolerância de relógio**, e só aceita HS256 (`alg: none` e outros algoritmos são recusados). O `JwtEncoder` também fica na #101, para os testes emitirem tokens e para o login (#103) usá-lo.
  - **Conteúdo do token:** `sub` (id do usuário, em texto), `role` (`ADMIN` ou `OPERATOR`), `iat`, `exp` (15 minutos) e `iss`. O `role` vira a autoridade `ROLE_ADMIN` ou `ROLE_OPERATOR` (é o que `hasRole` confere na #105); o Spring Security acrescenta a autoridade `FACTOR_BEARER`, que só registra como o usuário se autenticou.
  - **Limitação aceita:** como o access token é stateless, um usuário inativado continua com o token válido até ele expirar (no máximo 15 minutos). A #104 revoga os refresh tokens dele, mas não há consulta ao banco a cada requisição, que anularia a vantagem do stateless.
  - **Erros:** 401 e 403 saem em ProblemDetail, pelo mesmo `GlobalExceptionHandler` dos outros erros. O `AuthenticationEntryPoint` e o `AccessDeniedHandler` apenas repassam a exceção ao resolvedor de exceções do MVC; a mensagem é fixa e nunca diz por que o token foi recusado, e o 401 leva `WWW-Authenticate: Bearer`.
  - **OpenAPI:** esquema de segurança Bearer (JWT), exigido por padrão em todas as operações.
  - **`.env`:** no perfil `local`, que é o padrão (`spring.profiles.default=local`), a aplicação importa o `.env` da raiz (`application-local.properties`), então as variáveis não precisam ser exportadas à mão; uma variável do ambiente tem prioridade sobre o arquivo. Os testes ativam o perfil `test` (em `src/test/resources/config/application.properties`, que também traz um segredo só de teste), e por isso nunca leem o `.env` do desenvolvedor.
  - **Testes:** os testes de controller (`@WebMvcTest`) continuam usando a segurança padrão do Spring com `@WithMockUser`, porque a cadeia real não faz parte dessa fatia; a cadeia é coberta por testes `@SpringBootTest` próprios (`SecurityChainTest`, `SecurityHandlersTest`, `JwtConfigurationTest`). A adaptação dos testes de controller ao perfil de cada rota fica na #105.
- **Refresh tokens** (issue #102): `V4__create_refresh_token.sql` cria a tabela `refresh_token` (`id`, `user_id`, `token_hash`, `expires_at`, `revoked_at`, `replaced_by`, `created_at`). O token é opaco (aleatório), então só o hash é guardado (`varchar(64)`, o tamanho de um SHA-256 em hexadecimal; um hash rápido basta porque o token tem alta entropia, ao contrário de uma senha), com índice único; não existe coluna para o token em texto. A chave estrangeira para `app_user` não tem cascata de propósito: um usuário com tokens não pode ser apagado, só inativado (RN14). A rotação e a revogação usam `revoked_at` e `replaced_by` (chave estrangeira para o token que o substitui), com três restrições de integridade: um token só expira depois de criado, um token substituído está sempre revogado, e nenhum token substitui a si mesmo. `created_at` não tem valor padrão no banco: a data vem do `Clock` da aplicação, como as demais. Todas as datas são `timestamptz`. Verificada por `RefreshTokenMigrationTest` com Testcontainers.
- **Login** (issue #103; RF08, HU05, RNF07, RNF08): `POST /api/v1/auth/login` recebe `login` e `senha` e devolve `200` com `{ "accessToken", "tokenType": "Bearer", "expiresIn": 900 }` (segundos). O **refresh token nunca vai no corpo**: vai no cookie `refresh_token`, `HttpOnly`, `Secure` (ligado por padrão; os navegadores também o aceitam em `http://localhost`), `SameSite=Strict` (decidido em 15/10/2026: front-end e API no mesmo site), `Path=/api/v1/auth` e `Max-Age` de 7 dias; tudo configurável em `app.auth.*` (`SameSite=None` só é aceito com `Secure`, e a aplicação não sobe com uma combinação que os navegadores recusariam). O front-end precisa fazer a requisição com credenciais (`credentials: 'include'`).
  - **Estrutura:** o login é do módulo `security`, mas quem confere as credenciais é o módulo `user`, por uma porta de entrada pública, `AuthenticateUserUseCase`, que devolve só o id e o perfil (`AuthenticatedUser`) e é dona de `canAuthenticate` e do `PasswordHasher` (que ganhou `matches`). O `LoginService` do `security` chama essa porta, cria o refresh token e pede o access token ao `AccessTokenIssuer` (JWT, com `sub`, `role`, `iss`, `iat` e `exp`; 15 minutos, em `app.jwt.access-token-ttl`).
  - **Refresh token:** o texto é gerado por `SecureRandom` (32 bytes, Base64 URL, 43 caracteres) e guardado só como SHA-256 em hexadecimal (`TokenHash`); `RefreshToken.issue` define a validade a partir da data recebida (do `Clock`). Nada é emitido nem gravado quando as credenciais são recusadas.
  - **Falha sempre igual:** login inexistente, senha errada e usuário inativo devolvem o mesmo `401` em ProblemDetail ("Login ou senha inválidos."), sem cookie e sem nada que diga qual foi o motivo (`InvalidCredentialsException`, com mensagem fixa). A senha é conferida sempre, contra um hash falso gerado pelo próprio `PasswordHasher` quando o login não existe, para o tempo de resposta não revelar quais logins existem. O limite de tentativas está descrito no item "Bloqueio por tentativas de login", abaixo.
  - **Cabeçalho `Authorization` nas rotas de autenticação:** é ignorado em `/api/v1/auth/**`. Sem isso, um front-end que reenvia o access token expirado ao fazer login de novo receberia `401` mesmo numa rota pública.
  - **CORS:** passou a permitir credenciais (`Access-Control-Allow-Credentials: true`), o que só é seguro com origens exatas; um `*` em `APP_CORS_ALLOWED_ORIGINS` faz a aplicação recusar a subir.
  - **Segredos:** a senha e os tokens ficam fora de `toString` e de log (comando, resposta, resultado e entidade de domínio), e um teste de integração confere o log.
- **Bloqueio por tentativas de login** (decidido em 15/10/2026, dentro da #103; RF08): depois de **3 senhas erradas** seguidas (`app.login-lockout.max-failed-attempts`), o usuário fica bloqueado por **15 minutos** (`app.login-lockout.block-duration`) e o bloqueio **termina sozinho**; o desbloqueio manual pelo ADMIN vem com a edição de usuário (#108). Decisão do dono do projeto: bloqueio automático por tempo, e não permanente, porque o bloqueio permanente deixaria qualquer pessoa trancar o administrador (e, se ele for o único usuário, o sistema inteiro) só digitando senhas erradas.
  - **Estado:** a migração `V5__add_login_lockout_to_app_user.sql` acrescenta `failed_login_attempts` (não negativo) e `blocked_until` (`timestamptz`, nulo = não bloqueado) a `app_user`; a V3 não foi editada. O bloqueio é um instante, então expira sem nenhuma tarefa em segundo plano.
  - **Regras no domínio** (`User`): `registerFailedLogin(agora, limite, duração)` conta a tentativa errada e bloqueia na que atinge o limite; **não conta** para usuário inativo nem já bloqueado, e por isso não prolonga o bloqueio; um bloqueio que já terminou é limpo antes e começa uma rodada nova de 3. `registerSuccessfulLogin()` zera a contagem. `canAuthenticate(agora)` é falso se inativo ou bloqueado, e `unblock()` (para o ADMIN, #108) zera tudo. O instante vem por parâmetro, do `Clock`.
  - **Resposta igual:** o usuário bloqueado recebe o mesmo `401` genérico de qualquer outra falha, sem dizer que a conta está bloqueada (dizê-lo revelaria que o login existe); a senha continua sendo conferida, com o mesmo custo de tempo.
  - **Simultaneidade:** o `UserRepository.findByLoginForAuthentication` trava a linha (`SELECT ... FOR UPDATE`) até o fim da transação, então tentativas em paralelo no mesmo usuário são contadas uma a uma; sem isso, 100 requisições simultâneas leriam todas a mesma contagem e burlariam o limite. Além disso, a recusa é uma exceção, e por padrão uma exceção desfaz a transação e, com ela, a gravação da tentativa errada. Por isso o `authenticate` **e o `LoginService.login`** usam `noRollbackFor = InvalidCredentialsException`: o `authenticate` participa da transação do `LoginService`, e é a transação externa que decide; só o `authenticate` não bastava, como a execução real mostrou. O `LoginService` não grava nada antes da recusa, então não há o que desfazer; qualquer outra falha continua desfazendo tudo. Os testes que provam isso rodam **sem transação de teste** (`LoginLockoutConcurrencyTest`, com 12 tentativas em paralelo, e `AuthLoginLockoutEndToEndTest`, pela rota HTTP), porque uma transação de teste esconde exatamente esse comportamento.
  - **Limites conhecidos:** a contagem é por usuário, não por IP; quem testa poucas senhas em muitos logins não é barrado por este mecanismo, e um atacante ainda pode bloquear um usuário por 15 minutos de cada vez (o custo aceito da proteção).
- **Renovação do token, logout e CSRF** (issue #104; decidido em 15/10/2026; RF08, RNF08):
  - **Renovar** (`POST /api/v1/auth/refresh`, sem corpo; lê o cookie `refresh_token`): devolve `200` no mesmo formato do login (novo access token no corpo e novo refresh token no cookie). O refresh token vale **uma vez só** (rotação): o usado é revogado e aponta (`replaced_by`) para o novo. O perfil do novo access token vem do banco no momento da renovação, não do token antigo. Token ausente, desconhecido, expirado, revogado ou de usuário inativo devolve sempre o mesmo `401` ("Refresh token inválido, expirado ou revogado."), que **limpa o cookie** (`Max-Age=0`, mesmos atributos) para o navegador parar de enviá-lo; um token expirado não revoga nada.
  - **Reuso:** usar um token que já estava revogado (já trocado, ou encerrado no logout) é sinal de que ele pode ter vazado, então **todos** os tokens do usuário são revogados (todos os dispositivos) e a resposta é `401`. Um usuário inativo ou removido também perde todos os tokens ao tentar renovar. O usuário bloqueado pelo bloqueio de login (#103) ainda renova uma sessão que já estava aberta: aquele bloqueio protege a senha.
  - **Sair** (`POST /api/v1/auth/logout`): revoga o token do cookie (só esta sessão; as de outros dispositivos continuam) e limpa o cookie. Responde `204` **sempre**, também sem cookie ou com token desconhecido ou já revogado, e não diz se o token existia. O access token já emitido continua válido até expirar (no máximo 15 minutos), a limitação já aceita.
  - **CSRF:** as duas rotas agem sobre um cookie que o navegador envia sozinho, então exigem o cabeçalho `X-Requested-With: XMLHttpRequest` (sem ele, `403` em ProblemDetail, antes de tocar no token). Uma página de outro site não consegue enviar um cabeçalho personalizado sem passar pelo CORS, que só libera a origem do front-end (o cabeçalho foi acrescentado aos permitidos); isso vale com front-end na mesma origem ou em outra, e soma-se ao `SameSite=Strict` do cookie. **O front-end precisa enviar esse cabeçalho nas chamadas de refresh e logout**, além de usar `credentials: 'include'`. O login não exige o cabeçalho.
  - **Estrutura:** `RefreshTokenUseCase`, `LogoutUseCase` e `RevokeRefreshTokensUseCase` (no `security`) são implementados por `RefreshTokenService`; o módulo `user` ganhou a porta pública `FindActiveUserUseCase`, que devolve o id e o perfil atuais de um usuário ativo. `RevokeRefreshTokensUseCase.revokeAllOf(userId)` é a porta pública que a inativação (#109) e a redefinição de senha (#110) de usuário chamam para revogar os tokens do usuário. O token é revogado por `RefreshToken.revoke` e girado por `RefreshToken.rotate` (o domínio recusa girar um token já revogado).
  - **Simultaneidade e transação:** a linha do token é travada (`SELECT ... FOR UPDATE`) enquanto ele é usado, então duas renovações simultâneas com o mesmo token são tratadas uma depois da outra: só uma passa, e a outra encontra o token revogado (assim a cadeia não se bifurca). Como consequência, duas abas que renovam ao mesmo tempo com o mesmo cookie derrubam a sessão (a rotação estrita pedida na issue). O `refresh` usa `noRollbackFor = InvalidRefreshTokenException`, para que a revogação feita antes da recusa (reuso, usuário inativo) não seja desfeita pela exceção; o `AuthRefreshEndToEndTest` roda sem transação de teste justamente para provar isso e a concorrência.
  - **Fora do escopo:** tokens expirados e revogados ficam na tabela (a limpeza periódica é uma melhoria futura).
- **Autorização por perfil** (issue #105; RNF08): cada controller declara quem pode chamá-lo com uma de três anotações de `shared.adapter.in.web`, na classe ou em cada método: `@AdminOnly` (só `ADMIN`), `@AdminOrOperator` (`ADMIN` ou `OPERATOR`) e `@PublicEndpoint` (público de propósito). As duas primeiras são `@PreAuthorize` embutidas (o `MethodSecurityConfiguration` liga a segurança por método), então um erro de digitação num `hasRole` vira erro de compilação; a terceira só registra a decisão, porque o que deixa o anônimo entrar é a lista de rotas públicas da cadeia (`SecurityConfiguration`). Um método pode endurecer o padrão da classe (por exemplo, `@AdminOnly` num controller `@AdminOrOperator`).
  - **A regra é verificada no build:** o `ArchitectureTest` reprova qualquer `@RestController` com um endpoint sem acesso declarado, ou com mais de uma anotação no mesmo elemento. O `AccessRulesTest` roda a regra contra controllers-modelo para provar que ela de fato reprova (uma regra que aceita tudo seria pega ali). Um controller novo que esquece de decidir quebra o build, em vez de ficar aberto a qualquer usuário logado.
  - **Matriz** (anônimo recebe 401 em tudo que não é público; perfil sem permissão recebe 403 em ProblemDetail, com a mensagem fixa "Você não tem permissão para acessar este recurso.", sem dizer qual perfil serviria):

    | Rotas | `ADMIN` | `OPERATOR` | Anônimo |
    | --- | --- | --- | --- |
    | `/api/v1/books`, `/authors`, `/categories`, `/copies` (todas as operações) | sim | sim | 401 |
    | `/api/v1/readers`, inclusive `/{id}/block` e `/{id}/unblock` | sim | sim | 401 |
    | `/api/v1/users/**` (#106 a #110) | sim | 403 | 401 |
    | `/api/v1/library-configuration` (#139) | sim | 403 | 401 |
    | Empréstimos, devoluções, reservas, multas e relatórios (fases 3 e 4) | sim | sim | 401 |
    | `/api/v1/auth/login`, `/refresh` e `/logout` | público | público | público |
    | `/actuator/health`, `/v3/api-docs/**`, `/swagger-ui/**` | público | público | público |

  - **Perfil desconhecido:** um token bem assinado mas com `role` ausente, vazio, desconhecido ou em outra caixa (`admin`, `Operator`, `ROLE_ADMIN`) não chama rota nenhuma (403): só `ADMIN` e `OPERATOR`, exatamente assim, abrem as rotas protegidas.
  - **Limitação conhecida (ordem no Spring):** o `@PreAuthorize` é avaliado ao invocar o método, e a validação do `@Valid @RequestBody` e a conversão dos parâmetros acontecem antes, ao montar os argumentos. Por isso quem não tem permissão e manda um corpo **inválido** recebe 400 e não 403; com um corpo válido recebe 403 e **nada é executado nem gravado** (há teste). Os campos exigidos já são públicos no OpenAPI, então isso não revela segredo.
  - **Contrato:** toda operação que exige token documenta no OpenAPI o 401 e o 403 como ProblemDetail (as públicas ficam de fora, e uma resposta que a operação já documenta nunca é substituída).
  - **Testes:** os testes de controller (`@WebMvcTest`) importam o `MethodSecurityConfiguration` e rodam como `@WithOperator` (ou `@WithAdmin`); cada um prova que um perfil sem permissão e um usuário sem perfil recebem 403, e que `ADMIN` e `OPERATOR` passam. O `SecurityAuthorizationTest` prova a matriz com a cadeia real e tokens de verdade, usando um controller de teste `@AdminOnly` (ainda não há rota só de ADMIN).
  - **Para criar um controller novo:** anote-o com uma das três; as rotas de usuário (#106 a #110) e a de configuração da biblioteca devem ser `@AdminOnly`.
- **Criação de usuário** (issue #106; RF09, HU28, RNF07, RNF08): `POST /api/v1/users`, **só para `ADMIN`** (o `UserController` é `@AdminOnly`, vale para todas as rotas de `/api/v1/users` das issues #106 a #110; um `OPERATOR` recebe 403 e nada é criado). O corpo traz `login`, `password` e `role` (`ADMIN` ou `OPERATOR`, exatamente assim; outro texto devolve 400); a resposta é `201` com `Location` (`/api/v1/users/{id}`) e `{id, login, role, active}`: **nunca a senha nem o hash**.
  - **Regras:** a senha segue a política (8 a 25 caracteres, com maiúscula, minúscula, número e caractere especial) e a recusa devolve `422` com a mensagem que diz quais regras faltam, sem repetir a senha; ela é guardada só como hash BCrypt (o `PasswordHasher`). O login é obrigatório, sem espaços, com até 50 caracteres e guardado em minúsculas; um login repetido, mesmo com outra caixa, devolve `422` ("já existe um usuário com o login 'x'") e o primeiro usuário continua como estava. O usuário nasce ativo, sem tentativas falhas e sem bloqueio, e já pode entrar com a senha escolhida.
  - **Ordem no serviço:** a política de senha é checada primeiro (barato, e não gasta hash à toa), depois o hash e o `User.create` (que valida o login e o perfil), depois `User.validateUniqueLogin` com `existsByLogin`. A restrição única do banco é a última defesa contra duas criações simultâneas do mesmo login: o `UserPersistenceAdapter` a traduz no mesmo `422`, e o `UserCreationIntegrationTest` (sem transação de teste, 6 requisições em paralelo) confirma que só uma passa e que as outras recebem 422, não 500.
- **Consulta e listagem de usuários** (issue #107; RF09, HU28, RNF14; só `ADMIN`, como todo o `/api/v1/users`):
  - `GET /api/v1/users/{id}` devolve 200 também para usuário inativo e 404 em ProblemDetail para id inexistente. `GET /api/v1/users` é paginado (`page` a partir de 0, `size` de 1 a 100, `sort=campo[,asc|desc]`), com filtro `login` por trecho (sem diferenciar maiúsculas) e `active` (`true` por padrão); a ordenação aceita só `id` e `login` (padrão `login`, na ordem do collation do banco, que ignora a pontuação no primeiro nível). Qualquer outro campo de ordenação, `size` acima de 100 ou filtro inválido devolve 400. O `UserFilter` e o `findAll` já vinham da #99.
  - **Resposta** (`UserResponse`, a mesma do detalhe, da lista e da criação): `id`, `login`, `role`, `active`, `blocked` e `blockedUntil`. **`blocked` é calculado no momento da consulta** (o `Clock` do controller): é verdadeiro enquanto o bloqueio por 3 senhas erradas estiver em vigor, e `blockedUntil` só aparece nesse caso; um bloqueio que já terminou aparece como `blocked: false` e sem data, mesmo que a linha ainda guarde o instante. A contagem de senhas erradas não é exposta. **Nenhuma resposta traz a senha nem o hash**, o que um teste confere no esquema do OpenAPI e outro compara o corpo com os hashes do banco; a ordenação por `password_hash` (ou qualquer campo que não seja `id` ou `login`) é recusada com 400.
- **Edição de perfil e desbloqueio de usuário** (issue #108; RF08, RF09, HU28; só `ADMIN`):
  - **`PATCH /api/v1/users/{id}`** altera só o perfil (`role`: `ADMIN` ou `OPERATOR`); um campo omitido ou nulo mantém o valor, e `login`, `password`, `active`, `blocked` ou `id` no corpo são **ignorados** (o login nunca muda; a senha é da #110 e a inativação da #109). Devolve 200 com o usuário, 404 para id inexistente, 400 para perfil desconhecido e 422 na regra do último administrador. O perfil novo vale no próximo login e na próxima renovação do token; o access token já emitido mantém o perfil antigo até expirar (no máximo 15 minutos), a limitação já aceita do JWT sem estado.
  - **Regra do último administrador** (`User.changeRoleKeepingAnAdministrator`): um administrador **ativo** não pode deixar de ser administrador quando não resta outro administrador **ativo**. Manter o mesmo perfil, promover um operador e rebaixar um administrador **inativo** (que não contava) são sempre permitidos. **O bloqueio por tentativas de login não entra na conta**: um administrador bloqueado continua contando como administrador, porque o bloqueio termina sozinho; assim um bloqueio temporário não trava a regra.
  - **Corrida entre administradores:** dois administradores que se rebaixam ao mesmo tempo passariam os dois, cada um vendo o outro ainda como administrador, e o sistema ficaria sem nenhum. Por isso o serviço trava (`SELECT ... FOR UPDATE`) as linhas dos administradores ativos, em ordem de id, e só depois a do usuário editado: o segundo pedido espera, encontra o primeiro já feito e é recusado. A ordem fixa impede que duas edições esperem uma pela outra. O `UserRoleConcurrencyTest` (sem transação de teste, 6 rodadas) prova que sempre sobra exatamente um. Essa mesma trava e essa regra são as que a inativação (#109) deve reaproveitar.
  - **Carregar com trava para alterar** (`UserRepository.findByIdForUpdate`): gravar um usuário regrava a linha inteira, então uma leitura velha poderia sobrescrever o que outro administrador mudou ao mesmo tempo (uma senha nova, por exemplo). A edição e o desbloqueio carregam o usuário já travado.
  - **`POST /api/v1/users/{id}/unblock`** encerra na hora o bloqueio por tentativas de login e zera a contagem de senhas erradas (`User.unblock()`), então a senha certa volta a entrar em seguida; devolve 204, é idempotente (quem não está bloqueado não é regravado) e dá 404 para id inexistente. Vale também para administrador bloqueado, desde que outro administrador o faça; se for o único, o bloqueio termina sozinho em até 15 minutos. Desbloquear um usuário inativo não o reativa.
- **Inativação de usuário** (issue #109; RF09, HU28, RN14; só `ADMIN`): `DELETE /api/v1/users/{id}` devolve 204 e **nunca exclui fisicamente**: o registro, o login, o perfil e o hash ficam, e o usuário deixa de aparecer na listagem padrão (continua em `GET /{id}` com `active=false` e em `active=false`). **Idempotente:** inativar quem já está inativo é 204 e não regrava a linha, mas ainda revoga os refresh tokens que sobraram. Id inexistente é 404.
  - **O que a inativação faz:** o usuário não entra mais (o login o recusa como a qualquer falha, com o mesmo 401), não renova o token (a renovação o recusa e revoga os tokens que restarem) e **todos os seus refresh tokens são revogados na mesma transação** (`RevokeRefreshTokensUseCase.revokeAllOf`, a porta pública do módulo `security` criada na #104); se a revogação falhar, a inativação é desfeita junto. **O access token já emitido continua valendo até expirar (no máximo 15 minutos)**, a limitação já aceita do JWT sem estado; há um teste que prova isso.
  - **Regras (422):** ninguém inativa **a si mesmo** (o controller lê o `sub` do token para saber quem está agindo; sem um id numérico a requisição é recusada com 403, para não deixar a regra sem aplicação) e o **último administrador ativo** não pode ser inativado (`User.deactivateKeepingAnAdministrator`). Como na #108, o bloqueio por tentativas de login não tira o administrador da conta, e um administrador inativo não conta. Um administrador que já foi inativado mas ainda tem um access token válido também não consegue inativar o último administrador.
  - **Corrida:** o serviço reaproveita a trava da #108 (as linhas dos administradores ativos em ordem de id, depois a do usuário), então dois administradores que se inativam ao mesmo tempo são tratados um depois do outro e sempre sobra um (`UserDeactivationConcurrencyTest`, 6 rodadas, sem transação de teste).
  - **Dependência entre módulos sem ciclo:** o `security` precisa achar o usuário ativo (`FindActiveUserUseCase`) e agora o `user` chama o `security` para revogar os tokens. Se as duas pontes estivessem no mesmo bean, ele dependeria de si mesmo e a aplicação não subiria; por isso a busca do usuário ativo mora numa classe própria, a `ActiveUserFinder`, separada do `UserService`.
- **Redefinição de senha** (issue #110; RF09, HU29, RNF07; só `ADMIN`): `PUT /api/v1/users/{id}/password` com `{"password": "..."}` devolve 204 sem corpo. A senha nova segue a **mesma política** da criação (`PasswordPolicy`, 422 com as regras que faltam, sem repetir a senha), é guardada só como hash BCrypt e **nunca é devolvida nem registrada em log** (o `ResetUserPasswordCommand` e o `ResetUserPasswordRequest` escondem a senha no `toString`). Id inexistente é 404; senha ausente, em branco ou com mais de 128 caracteres é 400.
  - **Sessões:** todos os refresh tokens do usuário são revogados **na mesma transação** (`RevokeRefreshTokensUseCase.revokeAllOf`); se a revogação falhar, a nova senha é desfeita junto. Quem estava logado precisa entrar de novo; o access token já emitido continua valendo até expirar (no máximo 15 minutos), a mesma limitação do JWT sem estado. Os tokens de outros usuários não são tocados.
  - **Decisões:** o administrador pode redefinir a **própria** senha; o usuário **inativo** tem a senha trocada e continua inativo (a redefinição não reativa); o usuário é carregado com trava (`findByIdForUpdate`), para o novo hash não sobrescrever uma alteração feita ao mesmo tempo. A redefinição **não** desbloqueia o usuário atingido pelo bloqueio por tentativas de login: isso é o `POST /{id}/unblock` (#108).
- **Listagens sem N+1**: os autores do livro ficam em `book_author`, mapeados como coleção de IDs carregada sob demanda. Para a listagem paginada não disparar uma consulta por livro, a coleção usa `@BatchSize` com o tamanho máximo de página (issue #53), carregando os autores da página inteira em uma única consulta; `JOIN FETCH` foi descartado porque, com paginação, faz o Hibernate paginar em memória. Um teste com as estatísticas do Hibernate garante no máximo duas consultas por página.

- **Configuração da biblioteca** (issue #136; RF26, RN16, RNF03): `V6__create_library_configuration.sql` cria a tabela `library_configuration`, de **uma única linha** (`id` fixo em 1 por uma restrição `check`), com a política de penalidade (`FINE`, `SUSPENSION`, `BOTH` ou `NONE`), o valor diário e o teto da multa (`numeric(10,2)`), os dias de suspensão por dia de atraso e o teto da suspensão, o prazo de empréstimo, o limite de empréstimos simultâneos, o limite de renovações e o prazo de retirada de reservas. Todas as colunas são obrigatórias, para que nenhum valor volte a ser uma constante no código. A linha inicial traz os valores decididos em 10/10/2026 (multa de R$ 1,00 por dia com teto de R$ 10,00; suspensão de 1 dia por dia com teto de 365 dias) e os padrões de RN04, RN06, RN07 e RN13 (3 empréstimos, 14 dias, 2 renovações, 3 dias de retirada). As restrições recusam o que não faz sentido (prazo ou limite de empréstimos zerados, teto de multa abaixo de um dia de multa, valores negativos); multa diária zero e zero renovações são permitidos. O domínio valida as mesmas regras com mensagens para o usuário (issue #137).
- **Migração de empréstimos, multas e suspensões** (issue #145; RNF17, RNF03, RN03, RN05, RN15): `V7__create_loan.sql` cria `loan`, `fine` e `suspension`, com chaves para `copy` e `reader` e a coluna `version` (para o `@Version` dos adaptadores da #146). **Empréstimo ativo é o que não tem `return_date`**; não existe status `OVERDUE`. O índice único parcial `uq_loan_active_copy` (`copy_id` onde `return_date` é nulo) faz o banco recusar um segundo empréstimo ativo do mesmo exemplar (RN03), a última defesa quando duas requisições passam juntas pelo lock otimista. `fine.loan_id` é único (uma multa por empréstimo), o valor é `numeric(10,2)` positivo e a justificativa do abono existe se, e somente se, a situação é `WAIVED`. A suspensão termina depois de começar, e o encerramento antecipado só existe com justificativa e não passa do término calculado (RN15). As restrições repetem as invariantes das classes de domínio; as mensagens ao usuário continuam sendo do domínio. Índices para as consultas de leitor, exemplar e atraso (parcial sobre os empréstimos ativos) e para as multas pendentes por leitor.
- **Persistência de empréstimos, multas e suspensões** (issue #146; RF14, RNF14, RNF17, RN03, RN05): as portas `LoanRepository`, `FineRepository` e `SuspensionRepository` ficam em `loan.application.port.out`, na linguagem do domínio (`save`, `findById` e `findAll(filtro, PageQuery)`), com os filtros `LoanFilter` (leitor, exemplar e situação: ativo quando não tem devolução), `FineFilter` (leitor, empréstimo e situação) e `SuspensionFilter` (leitor, empréstimo e "em vigor num dia", com o mesmo significado de `Suspension.isInForce`). Toda listagem é paginada, com o máximo de 100 itens do `PageQuery`. As entidades JPA (`LoanJpaEntity`, `FineJpaEntity`, `SuspensionJpaEntity`) são separadas do domínio, com mapeamento explícito nos adaptadores e as referências como ids.
  - **Regras traduzidas:** a violação do índice `uq_loan_active_copy` vira `BusinessRuleException` ("o exemplar já tem um empréstimo ativo"), também na corrida entre duas requisições; a do `fine_loan_id_key` vira "o empréstimo já tem multa". Outras violações (um exemplar que não existe, por exemplo) seguem como `DataIntegrityViolationException`.
  - **Versão sem carregá-la no domínio:** as três entidades têm `@Version`, mas o domínio não a carrega. Para salvar um registro existente o adaptador **atualiza a entidade carregada na mesma transação** (só os campos que mudam: prazo, devolução e renovações no empréstimo; situação e justificativa na multa; encerramento antecipado e justificativa na suspensão), então a versão é a lida pelo caso de uso e uma alteração concorrente falha com `OptimisticLockingFailureException` em vez de sobrescrever. Por isso os casos de uso precisam ser transacionais (já é regra do projeto). Salvar um id que não existe é erro de programação (`IllegalStateException`).
  - **Testes:** `@DataJpaTest` com Testcontainers para os três adaptadores, `LoanConcurrencyTest` (dois empréstimos simultâneos do mesmo exemplar deixam um só ativo; duas transações no mesmo empréstimo não se sobrescrevem) e fakes em memória (`InMemoryLoanRepository`, `InMemoryFineRepository`, `InMemorySuspensionRepository`) que repetem as recusas do banco para os testes dos casos de uso.
- **Porta pública do catálogo para o empréstimo** (issue #147; RN03, RNF17, RNF02): o `loan` não toca nas classes internas do `catalog`, só nestas portas de entrada: `FindCopyAvailabilityUseCase` (devolve um `CopyAvailability(copyId, lendable)`, vazio se o exemplar não existe; `lendable` é exemplar ativo e `AVAILABLE`), `CheckOutCopyUseCase` e `CheckInCopyUseCase`. Elas são implementadas por `CopyLoanService`, classe à parte do `CopyService` e transacional: cada chamada é uma transação, então o caso de uso de empréstimo (#149) que a chama na sua própria transação desfaz as duas metades se uma falhar.
  - **Marcar como emprestado e devolver usa `Copy.checkOut` e `Copy.checkIn`**, não `Copy.changeStatus`: `BORROWED` só muda pelo fluxo de empréstimo e a rota manual continua recusando-o. `checkOut` só aceita exemplar ativo e `AVAILABLE` (RN03). `checkIn` torna `BORROWED` em `AVAILABLE`; **um exemplar `DAMAGED` ou `LOST` continua como está** (devolver não o conserta; ele só volta a disponível pela troca manual de status) e qualquer outro status é recusado.
  - **Lock otimista:** o `@Version` do exemplar já existente faz duas mudanças simultâneas não passarem as duas; a perdedora é recusada pela regra de negócio (viu o exemplar já emprestado) ou por `OptimisticLockingFailureException` (leu antes de a outra confirmar). O `CopyLoanConcurrencyTest` mostra que, de duas chamadas simultâneas de `checkOut`, só uma passa.
  - **Sem ciclo:** a dependência vai só do `loan` para o `catalog`. Uma regra do ArchUnit (`catalogShouldNotDependOnLoan`) quebra o build se o catálogo passar a depender do `loan`, o que faria os dois serviços dependerem um do outro (lição da `ActiveUserFinder`).
- **Porta pública do `user` para o empréstimo** (issue #148; RN11, RF10, RNF02): `GetReaderBorrowingStateUseCase.getBorrowingState(readerId)` devolve um `ReaderBorrowingState(readerId, active, blocked, canBorrow)` e lança `ResourceNotFoundException` (404) se o leitor não existe. O `canBorrow` é o veredito de `Reader.canBorrow` (ativo e não bloqueado) e `active` e `blocked` vêm junto, para o `loan` montar o `BorrowingSituation` (#149) e listar todos os motivos de recusa (um leitor inativo e bloqueado aparece com os dois). A suspensão não está aqui: é do `loan`. Implementada por `ReaderBorrowingStateService`, classe à parte do `ReaderService` e somente leitura, e o `loan` não importa nada interno do `user`. Uma regra do ArchUnit (`userShouldNotDependOnLoan`) mantém a dependência de uma via só.
- **Registro do empréstimo** (issue #149; RF11, HU07, RN03, RN04, RN05, RN06, RN11, RNF16, RNF17): `POST /api/v1/loans` (ADMIN e OPERATOR) recebe só `copyId` e `readerId` e devolve 201 com `Location` e o `LoanResponse` (`id`, `copyId`, `readerId`, `pickupDate`, `dueDate`, `returnDate`, `renewals`, `active`). **Nenhuma data é aceita no corpo**: a retirada é hoje, pelo `Clock`, e a data prevista soma o prazo da configuração (RN06, RN16). O `Location` aponta para `GET /api/v1/loans/{id}`, que chega com a consulta (#152).
  - **Orquestração (`RegisterLoanService`, uma transação, RNF16):** lê a configuração, cria o `Loan` (o que já valida os ids), levanta os fatos (o exemplar pela porta do `catalog` e o leitor pela do `user`; empréstimos abertos, empréstimo em atraso, multa pendente e suspensão em vigor pelos repositórios do `loan`, cada um por uma consulta que só conta), deixa o domínio decidir (`BorrowingEligibility.check`), marca o exemplar como emprestado e grava o empréstimo. Se qualquer passo falhar, nada fica: um teste sem `@Transactional` força a falha do último passo e confirma que o exemplar volta a `AVAILABLE`.
  - **Respostas:** cada motivo de recusa (RN03, RN04, RN05, RN11) vira **422** com todos os motivos na mesma mensagem; exemplar ou leitor que não existe é **404**; corpo sem `copyId` ou `readerId` é **400**; sem token, **401**. **409** é novo: `OptimisticLockingFailureException` passou a ser tratada no `GlobalExceptionHandler` ("tente novamente"), porque de dois pedidos simultâneos para o mesmo exemplar um pode ler o exemplar antes de o outro confirmar e perder no `@Version`; nada foi gravado, então repetir é seguro.
  - **Filtro de atraso:** `LoanFilter` ganhou `overdueOn` (empréstimo aberto com data prevista antes do dia, o mesmo significado de `Loan.isOverdue`); um teste compara a consulta com o domínio. O relatório de atrasos (#157) reaproveita o filtro.
  - **Fuso:** o `Clock` da aplicação agora é `America/Sao_Paulo` (decisão da #135), então "hoje" é o mesmo dia da biblioteca qualquer que seja o fuso do servidor.
  - **Concorrência:** `RegisterLoanConcurrencyTest`, sem `@Transactional`, mostra que dois empréstimos simultâneos do mesmo exemplar deixam um só (o outro é recusado pela regra ou pelo lock otimista). A aplicação também foi executada de verdade contra um PostgreSQL descartável: 201, 422 com um ou vários motivos, 404, 400, 401 e, em dois pedidos simultâneos, um 201 e um 409.
- **Devolução e penalidade** (issue #150; RF12, RF20, HU08, RN08, RN09, RN16, RNF16): `POST /api/v1/loans/{id}/return` (ADMIN e OPERATOR, sem corpo) devolve 200 com o `ReturnLoanResponse`: o empréstimo já encerrado (`loan`), os `daysLate` e, **nulos quando a política não aplicou nada**, a `fine` (`id`, `amount`, `status`) e a `suspension` (`id`, `startDate`, `endDate`). Empréstimo inexistente é 404, id que não é número é 400, empréstimo já encerrado é 422 (RN09), sem token é 401.
  - **Orquestração (`ReturnLoanService`, uma transação):** carrega o empréstimo e a configuração, deixa o domínio encerrar o empréstimo com a data de hoje e contar o atraso (`Loan.returnCopy`) e calcular a penalidade (`configuration.getPenaltyPolicy().calculate`), marca o exemplar como disponível pela porta do catálogo e grava o empréstimo, a multa e a suspensão. **Mudar a política é só configuração**; cada variante (`FINE`, `SUSPENSION`, `BOTH`, `NONE`) tem seu teste de serviço isolado, e os números e tetos vêm da configuração.
  - **A penalidade é calculada na devolução e guardada** (RN16): mudar a política depois não recalcula nada do que já foi devolvido, e a nova política vale só para as próximas devoluções. A suspensão começa no dia da devolução (#143). Um exemplar `DAMAGED` ou `LOST` continua como está ao voltar (#147).
  - **Tudo ou nada e corrida:** o teste de integração roda **sem `@Transactional`**, pelo caminho real. Um exemplar que diz estar disponível com o empréstimo aberto faz o último passo falhar e o empréstimo continua aberto, sem multa nem suspensão. Duas devoluções simultâneas do mesmo empréstimo deixam uma multa e uma suspensão só (uma responde 200 e a outra 409 ou 422).
  - **Execução real** contra um PostgreSQL descartável (com `SPRING_DOCKER_COMPOSE_ENABLED=false`, conferindo no log o banco usado): devolução em dia (200, nada aplicado), 6 dias de atraso com multa de R$ 6,00, segunda devolução (422), troca para `BOTH` com multa e suspensão de 6 dias sem tocar na multa antiga, o leitor recusado em novo empréstimo com os dois motivos, 404, 400, 401 e, em dois pedidos simultâneos, um 200 e um 409.
- **Renovação do empréstimo** (issue #151; RF13, HU09, RN07, RN09, RN16): `POST /api/v1/loans/{id}/renew` (ADMIN e OPERATOR, sem corpo) devolve 200 com o `LoanResponse`, já com a nova data prevista e a renovação contada. `RenewLoanService` só orquestra: carrega o empréstimo e a configuração e chama `Loan.renew`, que recusa empréstimo encerrado (RN09), em atraso e com o limite de renovações atingido (RN07), tudo com 422 e a mensagem do motivo; id inexistente é 404, id que não é número é 400, sem token é 401 e alteração simultânea do mesmo empréstimo é 409.
  - **Os números são da configuração** (RN16): o limite de renovações e o prazo somado (`loanPeriodDays`), que avança **a partir da data prevista atual**, então a renovação nunca dá menos tempo do que já havia. Limite zero recusa toda renovação.
  - **Ponto de extensão (Fase 4):** a RN07 também recusa a renovação quando outro leitor tem uma reserva pendente do livro. Como ainda não há reservas, nada é checado; está registrado no comentário do `RenewLoanService`: quando elas chegarem, o serviço busca esse fato por uma porta e o entrega ao domínio, como faz com os fatos do empréstimo.
  - **Testes:** serviço (limite e prazo da configuração, atraso, encerrado, inexistente, fuso), `@WebMvcTest` e integração sem `@Transactional`, pelo caminho real, com duas renovações simultâneas (ou passam as duas em sequência, ou uma perde com 409; nenhuma renovação respondida com 200 se perde). A aplicação também foi executada de verdade contra um PostgreSQL descartável: 200, 200, 422 no limite, troca de prazo e limite pela API refletida na renovação seguinte, 422 em atraso e encerrado, 404, 400 e 401.

## Como executar

1. Instale o JDK 25 e tenha o Docker em execução.
2. Na raiz do projeto, execute `./mvnw spring-boot:run`, ou rode a classe `BooksManagerApplication` pela IDE.
3. O Spring Boot sobe o PostgreSQL automaticamente a partir do arquivo `compose.yaml`.
4. A API responde em http://localhost:8080. A documentação Swagger fica em http://localhost:8080/swagger-ui.html.

Toda rota exige um token JWT válido, exceto as públicas (documentação Swagger/OpenAPI, health check e `/api/v1/auth/**`). O token é emitido por `POST /api/v1/auth/login` (issue #103) e renovado por `POST /api/v1/auth/refresh`, com `POST /api/v1/auth/logout` para sair (issue #104). A aplicação lê o arquivo `.env` da raiz no perfil `local` (o padrão) e exige a variável `APP_JWT_SECRET` (ver "Cadeia de segurança e JWT", em "Decisões tomadas").

O front-end é criado, executado e acompanhado separadamente, em seu próprio repositório; os comandos de instalação e execução ficam lá. Em desenvolvimento, a API precisa liberar o CORS para a origem do servidor de desenvolvimento do front-end.

Esse volume cobre os requisitos de prioridade M e deve deixar folga para boa parte dos itens S. Os itens S só entram depois que todos os M estiverem prontos e testados, e os C ficam para versões futuras.

- **Front-end separado, em repositório próprio.** React com Tailwind CSS, consumindo a API REST do backend, em um repositório diferente deste (decidido em 10/10/2026; descartada a opção de pasta `frontend/` no mesmo repo). A criação e o acompanhamento do projeto do front-end ficam nesse repositório, e por isso saem das pendências da Fase 0 deste (decidido em 14/10/2026). As dependências do Thymeleaf já saíram do `pom.xml`, e o backend expõe apenas a API. Ainda em aberto, e a decidir lá: build, TypeScript ou JavaScript, roteamento e cliente HTTP.
- **Autenticação por JWT com refresh token** (decidido em 10/10/2026; descartada a sessão no servidor, o backend não guarda sessão). Detalhes (decididos em 14/10/2026; RF08, RNF07, RNF08):
  - Access token JWT assinado com HS256 (resource server do Spring Security, Nimbus), segredo na variável de ambiente `APP_JWT_SECRET`; vida de 15 minutos.
  - Refresh token opaco (aleatório), guardado como hash em tabela, com rotação a cada uso e revogação (logout e inativação do usuário); vida de 7 dias. Entregue em cookie `httpOnly` (decidido em 15/10/2026 e confirmado com o front-end), o que exige CORS com credenciais e proteção contra CSRF na rota de renovação.
  - Autorização por perfil em cada endpoint (issue #105): usuários do sistema e configuração da biblioteca só para ADMIN; o restante, para ADMIN e OPERATOR.
  - Primeiro administrador criado na inicialização, por `APP_ADMIN_LOGIN` e `APP_ADMIN_PASSWORD`, somente se não houver usuário algum.
- **Leitores** (decidido em 14/10/2026; RF07, RF10, RNF11):
  - O `Reader` é um agregado separado do `User` do sistema, ambos no módulo `user`. Estados `active` e `blocked` agora; `suspendedUntil` só na Fase 3.
  - O documento é um texto genérico, normalizado e único (aceita CPF, matrícula etc.). O e-mail é obrigatório e o telefone é opcional, ambos validados. A data de nascimento é obrigatória, para saber se o leitor é menor de 18 anos.
  - Busca por nome com "contém" e por documento com igualdade. A listagem devolve o documento mascarado e não traz nascimento nem responsável; a consulta individual traz tudo.
  - Leitor menor de 18 anos exige os dados do responsável: nome e e-mail obrigatórios, telefone opcional. A idade vem da data de nascimento e de uma data de referência recebida por parâmetro, nunca de `LocalDate.now()` no domínio; ao completar 18 anos a exigência deixa de valer.
  - Estado do `Reader` (issue #89): `block`, `unblock` e `deactivate` são idempotentes; leitor inativo não pode ser bloqueado, mas o bloqueado pode ser inativado e continua bloqueado (para poder ser desbloqueado depois); `canBorrow` (RN11) é falso para inativo ou bloqueado, e a suspensão entra na Fase 3. Nome, e-mail e telefone não podem ter espaços nas pontas; o documento é normalizado (sem pontuação nem espaços, em maiúsculas).
  - Persistência do `Reader` (issue #90): porta `ReaderRepository` e `ReaderFilter` na aplicação, com entidade JPA separada e mapeamento explícito (como no `loan`, por ter regras de estado e dados pessoais). O documento duplicado é recusado pela restrição única do banco e traduzido em `BusinessRuleException`, também na edição. A listagem filtra por nome ("contém", sem diferenciar maiúsculas, `%` e `_` literais), documento (igualdade, normalizado como no cadastro), `active` e `blocked`; ordenável por `id`, `name` ou `document`.
  - Cadastro (issue #91): `RegisterReaderUseCase` e `ReaderService` carregam só o que o domínio precisa para decidir (se o documento já existe, por `Reader.validateUniqueDocument`) e a data de referência vem do `Clock`. No JSON o responsável é um objeto `guardian` (`name`, `email`, `phone`), ausente quando não informado; a resposta traz o documento completo, a data de nascimento e o responsável. Faltando e-mail, data de nascimento, nome ou documento, a resposta é 400; os campos do `guardian` não são obrigatórios no contrato porque quem decide é o domínio (menor de 18 anos sem nome ou e-mail do responsável devolve 422 com mensagem clara). Nenhum dado pessoal é registrado em log: não há log de SQL nem de corpo de requisição, e os serviços não logam.
  - Consulta (issue #92): `GET /api/v1/readers/{id}` devolve 200 também para leitor inativo ou bloqueado, com `active` e `blocked`, o documento completo, a data de nascimento e o responsável (quando houver); id inexistente devolve 404.
  - Listagem (issue #93): `GET /api/v1/readers` filtra por `name` (trecho), `document` (igualdade, normalizado), `active` (padrão `true`) e `blocked` (sem o parâmetro, ambos), e ordena por `id` ou `name` (padrão `name`); qualquer outro campo de ordenação, `size` acima de 100 ou filtro inválido devolve 400. O item da listagem (`ReaderSummaryResponse`) é separado do detalhe: traz `id`, `name`, `maskedDocument`, `email`, `active` e `blocked`, e não traz data de nascimento, responsável nem telefone. O documento sai mascarado (só os dois últimos caracteres aparecem; até quatro caracteres, tudo mascarado) para não expor documentos em massa; a consulta por id devolve o completo. O `ReaderSearchQueryCountTest` garante duas consultas por página (a página e o total), qualquer que seja o tamanho dela.
  - Edição (issue #94): `PATCH /api/v1/readers/{id}` segue a regra geral do `PATCH` (campo omitido ou `null` mantém o valor), então nenhum campo, inclusive o telefone e os dados do responsável, é apagado por essa rota. Só os dados pessoais de RNF11 são editáveis; `active` e `blocked` não, e são ignorados se vierem no corpo. Os campos do `guardian` enviados substituem os atuais um a um, e o domínio valida o estado resultante: informar uma data de nascimento de menor sem o responsável (nem no cadastro nem no mesmo pedido) devolve 422. A unicidade do documento é conferida com `existsByDocumentAndIdNot`, de modo que manter o próprio documento (mesmo escrito com pontuação) não é repetição, e trocar para o de outro leitor devolve 422.
  - Inativação (issue #95): `DELETE /api/v1/readers/{id}` inativa o leitor sem excluí-lo (RN14), devolve 204 também para quem já está inativo e 404 para id inexistente. O leitor inativo continua em `GET /{id}` com `active=false`, sai da listagem padrão e `canBorrow` é falso (RN11). Um leitor bloqueado pode ser inativado e continua bloqueado.
  - Bloqueio (issue #96): `POST /api/v1/readers/{id}/block` e `/unblock` devolvem 204, são idempotentes e devolvem 404 para id inexistente. Bloquear um leitor inativo devolve 422 (regra do `Reader`); desbloquear é permitido mesmo para o inativo que foi bloqueado antes de ser inativado. O leitor bloqueado tem `canBorrow` falso (RN11), `blocked` aparece na consulta e filtra a listagem. Não há motivo de bloqueio. O esquema fica pronto para anonimização futura (RN14 com a LGPD), inclusive dos dados do responsável, sem implementá-la.
- **Penalidade por atraso configurável.** A biblioteca escolhe, em configuração, entre multa, suspensão, ambas ou nenhuma (RF20, RF26, RN08 e RN16). O sistema não fixa essa escolha.
- **Valores iniciais da política de penalidade** (decidido em 10/10/2026): multa de R$ 1,00 por dia de atraso com teto de R$ 10,00; suspensão de 1 dia por dia de atraso com teto de 1 ano (ver nota em RN08 sobre o modelo de acúmulo assumido).
- **Domínio da configuração da biblioteca** (issue #137; RF26, RN16): `LibraryConfiguration` e o enum `PenaltyPolicy` (`FINE`, `SUSPENSION`, `BOTH`, `NONE`) ficam em `loan.domain`, em Java puro. Existe uma única configuração e ela sempre existe (a migração a cria), então a classe só tem `reconstitute` e `update`, sem criação. **`update` é parcial**: um valor nulo mantém o atual, as regras são conferidas sobre o resultado (um valor mantido também conta: subir a multa diária acima do teto atual é recusado) e, se algo for inválido, nada muda. As regras repetem as restrições do banco com mensagens em português (valor diário não negativo, teto da multa positivo e nunca abaixo de um dia de multa, dinheiro com no máximo duas casas decimais e até 99.999.999,99 (o valor é sempre guardado com duas casas, então `1.5` enviado volta como `1.50` no `PATCH` e no `GET`), fator e teto da suspensão, prazo de empréstimo, limite de empréstimos e prazo de retirada de pelo menos 1, renovações não negativas). Não há limite superior para os inteiros; quem fizer contas com eles (a política de penalidade, #140) deve usar `long`.
- **Persistência da configuração da biblioteca** (issue #138; RF26, RN16): a porta de saída `LibraryConfigurationRepository` (em `loan.application.port.out`) tem `get`, `getForUpdate` e `save`; como a configuração é única e sempre existe, não há busca que volte vazia nem criação, e uma linha ausente é um `IllegalStateException` (só ocorre se o banco foi adulterado). A entidade JPA `LibraryConfigurationJpaEntity` é separada do domínio, com mapeamento explícito no adaptador; o `id` é um `Short` (a coluna é `smallint`, fixa em 1) e nunca é gerado. **`getForUpdate` trava a linha** (`SELECT ... FOR UPDATE`) até o fim da transação: a edição regrava a linha toda, e sem a trava um administrador sobrescreveria, com uma leitura velha, o que outro acabou de mudar. O `LibraryConfigurationConcurrencyTest` (sem transação de teste, duas threads) prova que as duas mudanças sobrevivem; sem a trava, a segunda é perdida. O fake em memória usado nos testes de serviço (`InMemoryLibraryConfigurationRepository`) nunca devolve a instância guardada, como o adaptador.
- **Consulta e edição da configuração da biblioteca** (issue #139; RF26, HU13, RN16, RNF08; só `ADMIN`, o `LibraryConfigurationController` é `@AdminOnly`): `GET /api/v1/library-configuration` devolve as regras vigentes e `PATCH /api/v1/library-configuration` altera algumas. A configuração é única, então a rota não tem id e a resposta não traz o id. O `PATCH` segue a regra geral: campo omitido ou `null` mantém o valor; campos desconhecidos, inclusive `id`, são ignorados. A resposta de ambas é `LibraryConfigurationResponse`, com todos os campos obrigatórios no OpenAPI.
  - **Erros:** política desconhecida, valor de tipo errado, JSON quebrado e um decimal onde se espera um número inteiro (`1.5` em `loanLimit`) são **400**. Valor que quebra uma regra do domínio (prazo ou limite menor que 1, valor negativo, mais de duas casas decimais, teto da multa abaixo da multa diária) é **422**, com a mensagem que diz qual; nada muda. O `OPERATOR` recebe 403 e quem não está autenticado recebe 401.
  - **Leitura estrita dos inteiros:** o padrão do Jackson corta `1.5` para `1`, o que gravaria um valor que quem chamou não enviou. Por isso os inteiros do pedido usam o `WholeNumberDeserializer` (só este DTO; o resto da API não mudou).
  - **Simultaneidade:** o `update` carrega a configuração com a trava da #138 (`getForUpdate`), então dois administradores que mudam valores diferentes ao mesmo tempo não se sobrescrevem.
  - **Quando a mudança vale (RN16):** só para os atrasos futuros. Nada é recalculado no momento da alteração: a data prevista é fixada em cada empréstimo e a penalidade é calculada na devolução com a política vigente naquele momento (decisão da #135).
- **Política de penalidade por atraso** (issue #140; RF20, RN08, RN16): `PenaltyPolicy.calculate(daysLate, configuration)` devolve uma `Penalty` (valor da multa, com duas casas, e dias de suspensão). A variante é do próprio enum, então a devolução chama `configuration.getPenaltyPolicy().calculate(dias, configuration)` e **trocar de multa para suspensão é só configuração**. Cada variante usa apenas os números do que aplica: `FINE` ignora os da suspensão, `SUSPENSION` ignora os da multa, `BOTH` aplica as duas e `NONE` nunca penaliza.
  - **Contas:** multa = dias de atraso × valor diário, limitada ao teto; suspensão = dias de atraso × dias por dia, limitada ao teto, cada uma com o seu. O acúmulo é por dia, até o teto (decisão da #135); chegar exatamente ao teto não é cortado. Atraso zero ou negativo nunca custa nada. A multa é calculada em `BigDecimal` e a suspensão em `long`, sem estouro: a partir do primeiro número de dias que alcança o teto, o teto é devolvido antes de multiplicar (um fator que não divide o teto, como 2 por dia contra 365, também nunca o ultrapassa).
  - **`Penalty`:** só o resultado do cálculo. `hasFine()` é falso para multa zero (a `Fine` exige valor positivo), e `isNone()` diz que não há nada a aplicar. Transformá-la em `Fine` e `Suspension` cabe ao caso de uso de devolução (#150). O domínio não lê o relógio: os dias de atraso chegam por parâmetro.
- **Domínio do empréstimo** (issue #141; RF11, RF12, RF13, RN06, RN07, RN09): `Loan` em `loan.domain`, em Java puro, guarda o `copyId` e o `readerId` (não os objetos) e recebe toda data por parâmetro; o prazo, o limite de renovações e o período vêm da configuração, também por parâmetro (RN16).
  - **Criação:** `Loan.create(copyId, readerId, pickupDate, loanPeriodDays)` põe a data prevista em retirada + prazo (RN06) e começa ativo, com zero renovações.
  - **Atraso é derivado, não guardado** (decisão da #135): `isOverdue(hoje)` é verdadeiro só para empréstimo ativo e depois da data prevista (o próprio dia do vencimento ainda está em dia); `daysLate(hoje)` conta dias corridos, nunca é negativo e, para um empréstimo já devolvido, vale até o dia em que voltou, qualquer que seja a data perguntada.
  - **Devolução:** `returnCopy(hoje)` encerra e devolve os dias de atraso (zero se em dia ou antecipada), que alimentam `PenaltyPolicy.calculate` (#140). Devolver um empréstimo já encerrado (RN09) ou antes da retirada é recusado e nada muda.
  - **Renovação:** `renew(hoje, limite, prazo)` recusa o empréstimo encerrado (RN09), o em atraso (RN07) e o que já usou o limite (RN07; limite zero = nenhuma renovação), nessa ordem, sem alterar nada. **A data prevista avança o prazo a partir da data prevista atual**, não de hoje, para que a renovação nunca dê ao leitor menos tempo do que ele já tinha (decisão desta issue; a assinatura ganhou o prazo, que a issue não previa). A checagem de reserva pendente (RN07) entra na Fase 4.
- **Domínio da multa** (issue #142; RF21, HU10, RN05): `Fine` e `FineStatus` (`PENDING`, `PAID`, `WAIVED`) em `loan.domain`, em Java puro. A multa aponta para o empréstimo e para o leitor por id e nasce `PENDING` (`Fine.create(loanId, readerId, valor)`), com o valor vindo da `Penalty` da política (#140). O **valor é sempre positivo** (uma multa zero não é multa) e guardado com duas casas, até 99.999.999,99, como o banco.
  - **Resolve-se uma única vez:** `pay()` e `waive(justificativa)` só valem para uma multa pendente; pagar ou abonar uma multa já paga ou já abonada é recusado, com a mensagem de qual das duas aconteceu, e nada muda. A verificação de situação vem antes da justificativa.
  - **Abono exige justificativa** não vazia, guardada sem os espaços das pontas e limitada a 500 caracteres (`Fine.MAX_WAIVER_REASON_LENGTH`); sem ela a multa continua pendente. `reconstitute` recusa um estado incoerente (abonada sem justificativa, ou justificativa em multa que não foi abonada).
  - Só a multa **pendente** impede novo empréstimo (RN05): depois de paga ou abonada ela deixa de bloquear. Essa checagem entra na política de elegibilidade (#144).
- **Domínio da suspensão** (issue #143; RF20, RN15, HU11): `Suspension` em `loan.domain`, em Java puro, é um registro do módulo `loan` (decisão da #135) que aponta para o leitor e para o empréstimo que a causou por id. **Começa no dia da devolução e cobre os dias da penalidade a partir dele**: o leitor está suspenso da data de início até o dia anterior à data de término, que já está livre (3 dias a partir de 5/11 suspendem 5, 6 e 7 e liberam em 8/11). Os dias vêm da `Penalty` (#140).
  - **Termina sozinha, sem rotina:** `isInForce(dia)` é derivado da data perguntada; nenhuma tarefa agendada fecha a suspensão.
  - **Encerramento antecipado (RN15):** `endEarly(hoje, justificativa)` libera o leitor a partir de hoje e grava o dia e a justificativa; a data de término calculada fica como histórico. A justificativa é obrigatória, guardada sem espaços nas pontas e limitada a 500 caracteres (`Suspension.MAX_REASON_LENGTH`, escolha desta issue como na `Fine`), e é recusada se faltar **mesmo quando não há nada a encerrar** (entrada malformada é sempre erro). Encerrar uma suspensão que já terminou, sozinha ou antes, **não tem efeito**: devolve `false`, não altera nada e mantém a primeira justificativa. O retorno diz se há algo a salvar.
  - `reconstitute` recusa estado incoerente (término antes do início, encerramento antecipado sem justificativa, justificativa sem encerramento, ou encerramento depois do término calculado).
- **Elegibilidade para novo empréstimo** (issue #144; RF11, HU07, RN03, RN04, RN05, RN11, RN16): `BorrowingEligibility.check(situação, limite)` em `loan.domain`, em Java puro, decide se um leitor pode pegar um exemplar. Os fatos chegam prontos em um `BorrowingSituation` (exemplar disponível, leitor ativo, leitor bloqueado, empréstimos abertos, multa pendente, suspensão em vigor e empréstimo em atraso), então a regra não consulta nada nem lê o relógio; **quem levanta os fatos é a aplicação** (#149), usando a data do dia para "em vigor" e "em atraso" e as portas dos módulos `catalog` (#147) e `user` (#148). O **limite de empréstimos simultâneos vem da configuração**, nunca de uma constante.
  - **Regras:** exemplar indisponível (RN03); leitor inativo ou bloqueado (RN11); leitor com tantos empréstimos abertos quanto o limite (RN04; um a menos ainda pode); leitor com multa pendente, suspensão em vigor ou empréstimo em atraso (RN05). Uma suspensão em vigor conta uma vez, pois RN05 e RN11 a citam.
  - **Todos os motivos de uma vez:** cada regra que falha entra na lista, em ordem estável (exemplar, leitor, limite, multa, suspensão, atraso), e `check` lança uma `BusinessRuleException` com a mensagem em português juntando todos (`O empréstimo não pode ser feito: o leitor tem multa pendente; o leitor está suspenso.`), para o operador resolver tudo de uma vez em vez de descobrir um motivo por tentativa. `refusals` devolve a lista, vazia quando o empréstimo é permitido. Um limite menor que 1 ou uma situação ausente é erro de programação (`IllegalArgumentException`), não uma recusa.
- **Modelagem da Fase 3** (decidido em 17/10/2026, issue #135):
  - **Acúmulo da penalidade (RN08):** por dia de atraso, até o teto. Com os valores iniciais, 3 dias de atraso são R$ 3,00 de multa e 15 dias são R$ 10,00 (no teto); a suspensão segue o mesmo modelo (1 dia por dia de atraso, até 365 dias). Não existe valor fixo por empréstimo.
  - **A suspensão é um registro próprio do módulo `loan`** (`Suspension`: leitor, empréstimo, início, término e, se encerrada antes do prazo, a data e a justificativa; RN15). O `Reader` **não** tem o campo "suspenso até": o estado "em suspensão" é derivado da consulta ao `loan`. Assim a justificativa e o histórico ficam guardados, e o `loan` não escreve dentro do `user`. O `user` expõe só o estado próprio do leitor (ativo e bloqueado, RN11).
  - **Atraso:** a devolução depois da data prevista, em dias corridos e sem carência; devolver no dia do vencimento não é atraso. Dias de atraso = data da devolução − data prevista (e, para um empréstimo ainda ativo, hoje − data prevista). O `Clock` da aplicação usa o fuso `America/Sao_Paulo`, para que "hoje" seja o dia do operador (hoje ele usa o fuso padrão do sistema, o que muda no primeiro caso de uso do `loan`, issue #149).
  - **Bloqueio de novo empréstimo (RN05):** a multa pendente bloqueia até ser paga ou abonada, mesmo depois de a suspensão acabar e mesmo que a política mude depois para só suspensão. O empréstimo em atraso é **derivado** (empréstimo ativo com data prevista anterior a hoje): não há status `OVERDUE` guardado nem rotina agendada.
  - **Renovação e reservas (RN07):** na Fase 3 a renovação valida só o limite, o atraso e o empréstimo encerrado. A checagem de reserva pendente entra na Fase 4, com a porta de consulta de reservas; não se cria uma porta sem uso agora.
  - **Qual configuração vale (RN16):** a data prevista é fixada no empréstimo (mudar o prazo não altera empréstimos feitos), e a multa e a suspensão são calculadas **na devolução, com a política vigente naquele momento**. Devoluções já registradas nunca são recalculadas; um empréstimo que já estava atrasado quando a política mudou é penalizado pela política nova.
